# Hysteria2 / Xray Compatibility Audit

Audit date: 2026-10-08 (Asia/Shanghai).

## Scope And Conclusion

The existing generator was not fully adapted. Minimal fixes were required.
No production node database, deployed Core binary, server firewall, or running
user proxy was modified. The HY2 implementation was not rewritten.

The request supplied a parameter list, not a complete node-template JSON,
share URL with real credentials, or an identifiable deployed 3x-ui server
version. A synthetic fixture implementing that list was used. This is not
verification of a particular production server or an unseen template.

Target: Xray-core **v26.9.30**, published 2026-09-30, a prerelease.
The GitHub `/releases/latest` endpoint instead reports stable **v26.3.27**,
published 2026-03-27. Selecting only that endpoint would miss the newer target.
The official v26.9.30 tag resolves to commit
`b26a91de4f3294e26a0ad0a970b81a386a41f789`.

The release binary download did not complete on this network. Testing used an
unmodified official tagged source build with Go 1.27.0, identifying itself as
`Xray 26.9.30 ... Custom`. This is not a claim that the official release ZIP
was checksum-verified or that its executable was used.

## Four Distinct Representations

1. **3x-ui server inbound:** `protocol: hysteria`, `settings.version: 2`,
   authenticated `clients`/`users`, TLS certificates and server-side Salamander.
   It is not an outbound. Its actual Core version must determine its schema.
2. **HY2 URI:** `hy2://` or `hysteria2://`, auth, main address/port, SNI,
   ALPN, `obfs-password`, and the hopping `mport` parameter.
3. **v2rayN node:** `ProfileItem.Password`, `Address`, `Port`, `Sni`, `Alpn`,
   serialized `ProtoExtra` for native HY2 options, and `Finalmask` for advanced
   Core settings. No database columns were added.
4. **Xray client:** outbound `protocol: hysteria`, `settings.version: 2`,
   target address/port, `streamSettings.hysteriaSettings.auth`,
   TLS, `finalmask.quicParams`, and `finalmask.udp`.

The tested server listens only on UDP 56923. An isolated local UDP forwarder
receives 30000-40000 and forwards those packets to 56923, independently of the
server JSON. No client UDPHop mask was added to the server.
This is equivalent test coverage of receiving forwarded traffic, not a claim
that the user's existing iptables/nftables rules were inspected.

The server's isolated Freedom outbound has an explicit allow rule for the
three local echo/DNS test ports. Current Core otherwise blocks private
destinations for a HY2 inbound. This test-only rule is not a client change.

## Actual Generated Client And Field Differences

`hy2-client.redacted.json` is the complete generated client config, not just an
outbound excerpt. It matches the generator's `brutal-domain.json` structurally,
apart from redacted authentication, Salamander password and log-file paths.
The fixture's example hostname is intentionally non-production.

Force Brutal uses the same shape with `congestion: force-brutal`.
The original and advanced generated fixtures are in
`D:/v2rayN-master/build-check/hy2-audit/generated/`.

| Requested / source field | Client runtime mapping and difference |
| --- | --- |
| Hysteria2 v2 | Xray name is `hysteria`, not `hysteria2`; version 2 appears in outbound settings and hysteriaSettings |
| Main port 56923 | `outbounds[proxy].settings.port: 56923` |
| Server clients/auth | Client auth belongs to `hysteriaSettings.auth`; server clients are not copied |
| TLS / SNI / h3 | `security: tls`, `tlsSettings.serverName`, `alpn: ["h3"]`; certificate checks remain enabled |
| Salamander | `finalmask.udp[0].type: salamander` with its password |
| Brutal 100 mbps up/down | `finalmask.quicParams.brutalUp/Down: "100mbps"`; spacing is accepted equivalently by Core |
| Force Brutal | Explicit `congestion: force-brutal`; normal Brutal does not imply force |
| BBR | Explicit `congestion: bbr`, or inferred when both per-node bandwidth values are zero |
| mport 30000-40000 | `finalmask.udp[1].settings.remotePorts: "30000-40000"`; legacy colon ranges normalized |
| Hop interval 30 seconds | `settings.interval: "30"`; Core also accepts numeric 30 or a supported range |
| mode | Generator emits `intervalLocal,intervalRemote`; Core lowercases it internally |
| remoteIPs | Omitted for ordinary mport, meaning inherit the target address; advanced Finalmask IPv4/IPv6 CIDRs are retained |
| Old quicParams.udpHop | Removed from generated config; old saved custom JSON converted only in the runtime copy |
| QUIC receive windows / timers | Advanced custom Finalmask survives sharing, SQLite and runtime generation |
| Older-server compatibility | `quicParams.disableChromeParrot: true` added as a conservative HY2 default; an explicit custom false is preserved |
| QUIC Datagram | Enabled internally by HY2 Core, not an invented `quicDatagram` JSON property |
| method / network | Generator retains the existing `network: hysteria` alias, explicitly accepted by target Core |

**Bandwidth semantics:** official Core parses both `"100mbps"` and `"100 mbps"`
as **13,107,200 bytes/second**, because its multiplier is 1024-based.
That is 104.8576 decimal Mbps. This follows the requested literal template;
it is not a v2rayN conversion bug and must not be confused with a measured
public-network rate or a strict decimal 100 Mbps cap.

## Issues Found And Fixes

1. The generator emitted obsolete `quicParams.udpHop`, which the target's JSON
   parser can silently ignore. It now emits an actual `udphop` UDP mask.
2. Single-port `mport` was silently omitted by a delimiter-only condition.
   Single ports, comma lists, dash ranges and legacy colon ranges now generate.
3. Hopping plus Salamander requires **Salamander -> UDPHop in JSON**.
   `NewFinalMask` reverses the list before wrapping; its HandleDial check then
   requires UDPHop at index zero internally. A deliberately wrong initial
   ordering passed `run -test` but failed an actual dial with `incorrect index`.
   Generation and custom-runtime normalization were corrected and retested.
4. Explicit congestion selection was ignored; nonzero bandwidth always meant
   Brutal. The generator now honors the existing `CongestionControl` property,
   including force-brutal and BBR, while retaining old bandwidth-based defaults.
5. Import/save cleared ALPN. It now preserves explicit ALPN and defaults empty
   HY2 ALPN to h3; generation also supplies h3 for old saved empty values.
6. Sharing dropped bandwidth, interval, congestion and custom Finalmask.
   Export/import now retains these, including advanced QUIC params.
7. Deduplication ignored HY2 ports, interval, bandwidth and congestion.
   Distinct HY2 configurations are no longer treated as identical for those fields.
8. With the target Core's default Chrome parrot, the v26.6.1 server accepted
   TCP and DNS but timed out on 4000-byte UDP messages. The same endpoint,
   certificates, credentials, forwarder and traffic passed after setting
   `quicParams.disableChromeParrot: true`, including an actual 30-second hop.
   The generator now defaults HY2 to that compatibility setting, including
   custom legacy Finalmask when the option is absent. An explicit custom
   `false` is preserved for users who want the target Core's Chrome parrot.
   The older implementation's UDP reader has a fixed 1200-byte buffer; the
   current reader is larger, and Chrome parrot advertises a larger Datagram
   limit. The successful option A/B test supports this compatibility fix,
   rather than a claim that an old server was silently upgraded.

## Unresolved Limits And Deployment Notes

- No production credentials or endpoint were supplied. Public TCP/UDP/DNS,
  actual existing forwarding rules, physical-network IPv6, production
  old/new servers and sustained up/down throughput remain unverified.
- Old **nodes** are not the same as old **client cores**.
  v26.9.9 accepts the new generated client config. The existing v26.6.1 client
  executable rejects `udphop` as an unknown mask. Use the audited target Core
  for the new client format; do not infer all historical client binaries work.
- The user's unknown 3x-ui deployment and a complete user-authored template
  cannot be verified without their version/configuration. No server JSON,
  certificates or firewall rules were fabricated as production facts.
- Current official FinalMask docs contain both a new udphop section and stale
  quicParams.udpHop examples. The tagged source and runtime behavior prevail.
- Existing sing-box defaults and the one-time Core-default migration were not
  changed. Select Xray explicitly for the Xray-specific advanced config.
- HY2 defaults disable Chrome parrot for old-peer Datagram compatibility.
  This deliberately trades the new QUIC fingerprint impersonation default
  for the observed old/new-server interoperability. A modern-only node may
  explicitly set `Finalmask.quicParams.disableChromeParrot: false`; with that
  choice, the v26.6.1 large-UDP incompatibility remains.
- Advanced mode/remoteIPs/QUIC settings remain available through existing
  Finalmask JSON; this change does not add a new GUI editor for every Core option.
- Already lost or absent share-link parameters cannot be reconstructed from
  nothing. Legacy nodes without per-node bandwidth still use existing defaults.
- Realm combined with port hopping, Gecko, arbitrary other FinalMask stacks,
  global TUN interception and server masquerade are outside this targeted test.
